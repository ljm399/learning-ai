# 目标
修改/api/chat接口，让他解析data/workflow.json来决定执行哪些节点。

比如目前的data/workflow.json其执行逻辑为
1. 执行获取登录状态
2. 判断登录状态结果，如果已登录则继续，未登录则固定返回固定返回节点 3的固定内容给前端
3. 如果已登录，则执行查询攻略节点，该节点提供了固定文档。读取备用
4. 执行AI推荐商品节点，调用大模型给如AI推荐商品节点定义的system和prompt。
5. 获取到大模型返回后执行获取商品列表节点
6. 执行筛选商品节点。

# 类型说明
不同类型的节点有不同的逻辑
1. request-请求节点，根据用户配置的地址，参数请求接口
2. condition-条件判断节点，判断条件导向不同节点，注意判断条件为js代码，请解析后执行。
3. return-固定返回节点。该节点提供了固定的值，直接把改值res.write给前端。
4. document-该节点提供了固定的文档内容
5. ai-用于请求大模型
6. 到了end节点，则把最后一个节点的结果res.write给前端
# 数据说明

数据分为全局和节点结果，全局里储存userPrompt和token。节点结果为每一个节点执行完毕后的返回值，都存入一个对象里备用

后续其他的节点会消费这些数据
比如：
${nodeResults.node-1}代表着取node-1的结果
${globals.userPrompt}代表去全局变量中的用户原始提问
